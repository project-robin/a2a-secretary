The A2A (Agent2Agent) protocol is an open standard designed to enable communication and interoperability between independent AI agent systems . Its core concepts revolve around a three-layered architecture: a Canonical Data Model, Abstract Operations, and Protocol Bindings . The protocol provides built-in mechanisms for idempotency and duplicate message handling, and it addresses serverless timeout management through asynchronous operations like streaming and push notifications   .

## Core Concepts of the A2A Protocol

The A2A protocol is structured into three distinct layers :

*   **Layer 1: Canonical Data Model** This layer defines protocol-agnostic data structures using Protocol Buffers in `specification/a2a.proto` . Key data types include `Task` (stateful work unit), `Message` (communication turn), `AgentCard` (agent metadata), `Part` (polymorphic content), `Artifact` (task output), and `TaskState` (lifecycle enum) .
*   **Layer 2: Abstract Operations** This layer defines protocol-independent RPC method signatures for operations such as `SendMessage`, `SendStreamingMessage`, `GetTask`, `ListTasks`, `CancelTask`, `SubscribeToTask`, and push notification management .
*   **Layer 3: Protocol Bindings** This layer provides concrete mappings of the abstract operations and data structures to specific transport protocols like JSON-RPC 2.0 over HTTP/SSE, gRPC over HTTP/2, and HTTP/REST with JSON .

Other fundamental communication elements include :

*   **Agent Card**: A JSON metadata document describing an agent's identity, capabilities, endpoint, skills, and authentication requirements .
*   **Task**: A stateful unit of work with a unique ID and defined lifecycle, facilitating long-running operations and multi-turn interactions .
*   **Message**: A single turn of communication between a client and an agent, containing content and a role ("user" or "agent") .
*   **Part**: The fundamental content container within `Messages` and `Artifacts`, holding text, file references, or structured data .
*   **Artifact**: A tangible output generated by an agent during a task, such as a document or image .

## Idempotency and Duplicate Message Handling

The A2A protocol provides mechanisms for idempotency :

*   **Get operations** (`Get Task`, `List Tasks`, `Get Extended Agent Card`) are inherently idempotent .
*   **Send Message** operations *may* be idempotent, and agents can use the `messageId` to detect duplicate messages .
*   **Cancel Task** operations are idempotent, meaning multiple cancellation requests have the same effect . A duplicate cancellation request might return `TaskNotFoundError` if the task has already been canceled and purged .

## Serverless Timeout Management

The A2A protocol is designed for asynchronous task execution and handles long-running tasks through several mechanisms  :

*   **Asynchronous Processing**: Operations return immediately with either `Task` objects or `Message` objects, and processing continues in the background when a `Task` is returned .
*   **Streaming with Server-Sent Events (SSE)**: Clients can initiate a stream to receive real-time, incremental results or status updates for tasks that produce incremental results or require ongoing updates . The stream terminates when the task reaches a terminal or interrupted state .
*   **Push Notifications**: For very long-running tasks or disconnected scenarios, the server can send asynchronous notifications to a client-provided webhook when significant task updates occur . The `PushNotificationConfig` includes a URL for the webhook and optional authentication details . Agents are responsible for attempting delivery at least once and may implement retry logic with exponential backoff for failed deliveries . They should also include a reasonable timeout for webhook requests (recommended: 10-30 seconds) .
